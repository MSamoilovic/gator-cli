# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`gator` — a CLI RSS feed aggregator in Go, backed by PostgreSQL. Started as the Boot.dev backend course project; everything beyond the core (users/feeds/follows/aggregation) is the maintainer's own extension work — see `docs/roadmap.md` for what's done and what's next.

## Commands

```bash
go build ./...            # build
go vet ./...              # vet
gofmt -l .                # list unformatted files (should be empty)
gofmt -w .                # format
go test ./...             # all tests; database-backed ones skip unless GATOR_TEST_DB_URL is set
go test -run TestParsePubDate ./...   # single test
```

### Database-backed tests

`internal/testdb` gives tests a real Postgres. They **skip** unless `GATOR_TEST_DB_URL` is set:

```bash
createdb gator_test                     # once; any name containing "test"
export GATOR_TEST_DB_URL="postgres://postgres@localhost:5433/gator_test?sslmode=disable"
go test ./...
```

`testdb.Open(t)` returns a `*DB` embedding `*database.Queries`, plus fixture helpers (`User`, `Feed`, `Follow`, `Post`, `Bookmark`, `MarkRead`) and raw escapes (`Count`, `Exec`, `QueryRow`). Three properties matter:

- **It applies `sql/schema` itself**, executing each file's `-- +goose Up` half, so the tests need no `goose` run and always match the migrations on disk. That works only because no migration uses `+goose StatementBegin` or `NO TRANSACTION`; one that did would need the real goose.
- **Each test binary gets its own schema**, named after the binary (`gator_test_database`, `gator_test_feeds`), dropped and recreated at first use. That is what makes `go test ./...` safe while Go runs packages in parallel — an earlier design used one shared schema and the packages wiped each other mid-migration. `public` is never touched.
- **Tests run on a plain connection, not in a rolled-back transaction**, with `TRUNCATE` between them. A transaction would be faster and better isolated, but `feeds.Add` and `feeds.Scrape` deliberately provoke a `23505` and carry on, and in Postgres a failed statement aborts the whole transaction — so the paths most worth testing are exactly the ones a transaction cannot cover.

`checkSafe` refuses a `GATOR_TEST_DB_URL` that is not loopback, or whose database name does not contain `test`, because setup drops a schema there. CI runs these against a `postgres:16` service and then asserts that none of them skipped — a silent skip would leave the suite green while testing nothing.

### Database

Schema and queries are **not** hand-written Go — they're generated. After editing anything under `sql/`:

```bash
goose -dir sql/schema postgres "$DB_URL" up   # apply migrations
sqlc generate                                  # regenerate internal/database/
```

`sql/schema` is also embedded into the binary (`//go:embed` in `main.go`, threaded through
`state.Schema`) and applied by `gator init` / `gator migrate` through `internal/migrate`, which drives
goose as a library. Both paths read the same files and share one `goose_db_version`, so they never
disagree — but a **new migration must be added under `sql/schema`**, never anywhere else, or only one
of the two will see it.

Never edit `internal/database/*.sql.go` by hand; it is sqlc output (`sqlc.yaml` → `out: internal/database`).

### Running

Requires `~/.gatorconfig.json` with `db_url` (and `current_user_name`, written by `login`/`register`). `gator init` creates it — atomically, at `0600`, and **only after the connection is proven and the schema applied**, so a wrong `--db-url` leaves no config behind. It refuses to overwrite an existing config without `--force`. `internal/config` rewrites the file atomically (temp file in the same directory, then `os.Rename`), so a crash mid-write cannot truncate it. Local dev Postgres runs on a non-default port; the connection string lives in that config file, not in the repo.

### Releasing

`.goreleaser.yaml` builds `gator` for linux/darwin/windows × amd64/arm64 and stamps the tag into `internal/cli.version` via `-ldflags -X`. Validate without releasing:

```bash
goreleaser check
goreleaser build --snapshot --clean
```

Pushing a `v*` tag runs `.github/workflows/release.yml`, which hands the whole thing to goreleaser: six binaries, archives, checksums, a GitHub release, and a Homebrew cask pushed to `MSamoilovic/homebrew-tap` (needs the `HOMEBREW_TAP_TOKEN` secret). It brings up a `postgres:16` service too, because goreleaser's `before` hook runs `go test ./...` and the database tests would otherwise skip.

`.github/workflows/ci.yml` gates every push on gofmt, vet, tests and a cross-compile matrix — **keep `gofmt -l .` empty or CI goes red.**

The module path is `github.com/MSamoilovic/gator-cli` and must stay matched to the repository: `go install github.com/MSamoilovic/gator-cli@latest` is an advertised install route, and the `-X .../internal/cli.version` ldflag silently sets nothing if the path drifts — which is exactly what happened while the module was called plain `gator-cli`.

## Architecture

**Command dispatch.** One table, `allCommands()` in `internal/cli/cli.go`, is the single source of truth: it carries each command's name, args, summary, group and handler, and from it are derived the registry (`command.go`), the interactive picker and `gator help`. A command sets exactly one of `run` (needs config + DB) or `runAuth` (also needs a logged-in user) — `needsLogin()` reads `runAuth != nil`, so the middleware wrapping and what the menu claims can never drift apart. `noDB: true` marks the commands that run before a config exists (`init`, `version`, `help`); `cli.Run` only opens config and Postgres when the chosen command actually needs them, so a fresh install can still run those three. `migrate` is **not** `noDB` — it needs the connection the config names, just not a migrated schema, and it reaches the raw handle through `state.DB` (the only command that does). `main.go` is now just the embed plus `cli.Run`. A handler is just `handlerFunc` = `func(context.Context, *state, command) error`, with the one root `context.Background()` in `cli.Run` — errors bubble up to `main` which prints and exits 1. Handlers never call `os.Exit` themselves.

**Auth middleware.** Commands needing a logged-in user are wrapped in `middlewareLoggedIn` (`middleware.go`), which converts the signature to `func(context.Context, *state, command, store.User) error` by calling `s.Store.Me(ctx)`. "Logged in" is purely a username in the config file — there are no passwords or sessions.

**That middleware is where a dead server token actually surfaces, not the TUI.** `Me` runs *before* the handler, so against a server with an expired token `gator tui` never starts and the TUI's own error screen is unreachable — measured against a real `gator serve`, it printed `can't execute tui: user not logged in: invalid token`. `signInError` therefore translates `store.ErrUnauthorized` and `store.ErrUnreachable` into `not signed in to <server> — run: gator login --server <server>` and `cannot reach <server> — … or run gator logout …`, and keeps the old wrap when `ServerURL` is empty because neither cause exists locally. The TUI's screen still matters for a token that dies mid-session; both paths are needed and neither covers the other.

**`internal/store` is the client-side seam, and it carries no `userID` argument anywhere.** A `store.Store` is bound to one identity when it is constructed (`local.New(q, cfg.CurrentUserName)`), so there is structurally no parameter into which another user's id could be written — that is the answer to multi-tenancy, enforced by the type system instead of 22 remembered checks. `local.Store` resolves the user lazily under a mutex, because the TUI calls the store from `tea.Cmd` goroutines, and memoizes **only on success** so a cancelled first call cannot cement an error for the life of the process. Add new per-user reads and writes here, not as fresh `s.Db` calls.

`state` still carries `Db *database.Queries` alongside `Store`, and four groups legitimately use it. Keep them there: `agg`/`prune`/`scrapeFeeds` (the aggregator always runs next to Postgres and never gets a remote implementation), `reset` (`CountAllRows`/`TruncateAll` must not exist on a client), `feeds` (the global feed directory, not per-user), and `register`/`login`/`users`. That last group is the subtle one — **those commands change the identity**, so the store built from the pre-login `CurrentUserName` would answer for the wrong user; `printNextStep` therefore must keep going through `s.Db`.

`store.Post`, `store.User` and friends are **type aliases** for the sqlc rows, which is what keeps `internal/tui` from having to rewrite 68 type references. `store.PostQuery` unifies filtering and search, but `local.Posts` still picks between `GetPostsForUserFiltered` and `SearchPostsForUser` on `q.Query != ""` — merging the two queries is a separate SQL change.

**`store.Store` has a fake: `internal/store/storetest`.** It is how `internal/cli` and the TUI's command layer are tested at all, so a new interface method needs a fake implementation too (a compile-time `var _ store.Store = (*Fake)(nil)` will tell you). Two traps live in those tests: `capture` in `internal/cli/handlers_test.go` swaps `os.Stdout` for a pipe, so **those tests must not run in parallel**; and `pressing[T]` in `internal/tui/store_test.go` runs the returned `tea.Cmd`s **concurrently with a timeout**, because `tea.Batch` mixes the store command with `expireStatus`, which is a `tea.Tick(3s)` and blocks when called. Draining a batch sequentially took six tests from 0.02s to 12s.

**`FollowURL` always names the feed, even when nothing was created.** `feeds.Follow` ends in `ON CONFLICT DO NOTHING`, which returns no row, so the `CreateFeedFollowRow` comes back zero-valued on an already-followed feed; `local.FollowURL` fills it in from the feed it already fetched. Returning the raw row printed `Already following ` with no name.

**Bare `gator`** opens a command picker (`internal/menu`, Bubble Tea) instead of erroring. It offers only what can actually work: with no reachable database just `version`/`help`, logged out only the guest commands, logged in everything visible (`reset` is `hidden`). The chosen command runs **after** the picker exits, or `tui` and `discover` would nest one Bubble Tea program inside another. A pipe gets the usage text on stderr and exit 1.

**Handlers are split by domain**, all in `package cli`: `users.go`, `feeds.go`, `bookmarks.go`, `categories.go`, `discover.go`, `opml.go`, `stats.go`, `article.go`, `prune.go`, `reset.go`, `service.go`, `setup.go`, `tui.go`, `version.go`. Logic shared with the TUI lives in `internal/feeds` (`Add`, `AddMany`, `Follow`, `Scrape`, `ScrapeAll`, `Prune`, `ParsePubDate`) — handlers keep only argument parsing and printing. `feeds.Add` validates a URL by actually fetching it, derives the name from `<title>` when none is given, and treats an already-known URL as "follow it" rather than an error.

**Aggregation loop.** `agg <duration>` ticks on a `time.Ticker`; each tick calls `feeds.ScrapeAll`, which picks up feeds via `GetFeedsToFetch` and fans out one goroutine per feed under a `sync.WaitGroup`, **capped at `maxParallelScrapes` (8) in flight by a `sem chan struct{}`** — the same pattern `addAll` uses for `maxParallelAdds`. It returns a `[]feeds.Result` and optionally calls an `onResult` callback per finished feed (serialized under a mutex) so the CLI can print progress live while the TUI takes the summary. Duplicate posts are expected — `errors.As` on `*pq.Error` code `23505` skips them. Shutdown is via `signal.NotifyContext`.

**That cap is not a nicety — without it healthy feeds get blamed for the aggregator's own saturation.** `ScrapeAll` used to start one goroutine per feed with no limit. Measured on 160 real followed feeds: fired all at once, **85 of 160 timed out**; capped at 8, 160 of 160 succeeded, for 5 seconds more wall time (15s vs 10s) — nothing against a 15-minute tick. The feeds were never broken; each of the ones that "failed" answers in under half a second on its own. The damage compounds because `feeds.Scrape` records health around `rss.FetchFeed`, so a timeout gets written to `last_error`/`failure_count` as if the publisher were at fault, and then `gator feeds` and the TUI feed pane mark it `⚠` — the maintainer's own database had 96 of 142 feeds flagged this way, all self-inflicted. `TestScrapeAllBoundsHowManyFeedsItFetchesAtOnce` counts peak in-flight requests against an `httptest` server and fails if the cap is lifted; it reported 40 of 40 before the fix.

**`supervise`** (`service.go`) re-execs the binary as `<self> agg <interval>` in its own process group, restarts it with exponential backoff (1s→60s, reset after 30s of healthy uptime), tees output to stdout and `gator-agg.log`, and forwards SIGINT/SIGTERM to the child. The three things that differ per OS — the signal set, the process group, and how the child is stopped — live behind `shutdownSignals()`, `isolateProcessGroup()` and `terminate()` in `service_unix.go` / `service_windows.go`. **Nothing else in the codebase may import `syscall` directly**; that is what broke the Windows build for weeks.

**The read axis is one tri-state, not a flag plus a view.** `GetPostsForUserFiltered` takes `@read_filter::text` with `all`/`unread`/`read`, and `store.PostQuery.Read` carries it as a `store.ReadState`. The first clause of the SQL is `@read_filter::text NOT IN ('unread','read') OR ...`, so **the zero value means "all"** and a `store.PostQuery{}` behaves as it always did; the API still validates the query parameter so `?read=typo` is a 400 rather than silently everything. There is no `GetReadPostsForUser` and no `GET /v1/posts/read` — `?read=read` replaces both and is paged, which the old query was not. In the TUI `U` and `H` act on this one axis (pressing either twice returns to `all`) and `esc` clears it; the list title shows `Read` or `· unread`, because the status line expires after 3s and the filter would otherwise be invisible. `uiState.UnreadOnly` stays a `bool` so old state files need no migration, and the read-only view is deliberately **not** persisted. One thing was given up on purpose: the old read view sorted by `post_reads.read_at DESC` ("what I read lately"); the merged query sorts by `published_at` like every other view, which is what lets `S` work inside it.

**Dynamic SQL in sqlc.** `GetPostsForUserFiltered` and `SearchPostsForUser` push optional filtering/sorting into SQL using named params (`@feed_name::text = '' OR ...`, `@feed_id::uuid = '000...'::uuid OR ...`, `@read_filter::text NOT IN (...) OR ...`, `CASE WHEN @sort_dir::text = 'asc' THEN ...`) rather than string-building queries in Go. Follow this pattern for new filters.

**`gator reset` (`reset.go`) truncates all seven tables**, it does not delete users and let cascades do the rest — after migration 014 that would have left orphan feeds and posts behind, because `feeds.user_id` no longer cascades. `TruncateAll` names every table explicitly and deliberately omits `goose_db_version`, so the schema and migration history survive and the database is usable immediately. Three guards: `localDatabaseName` refuses any `db_url` that is not loopback, the row counts are printed first, and `confirm` requires the database name typed in full rather than `y`. `--yes` skips only the prompt; `--dry-run` skips the delete. `isTerminal` is the `os.ModeCharDevice` check, which counts `/dev/null` as a terminal — the name-match is what actually stops an unattended delete, not that check.

**Deleting a user must not delete anyone else's data.** `feeds.user_id` is nullable and its FK is `ON DELETE SET NULL` (migration 014) — the column means "who first added this feed", not "who owns it". Before that it was `ON DELETE CASCADE`, which chained `users` → `feeds` → `posts` → every other user's `feed_follows`, `bookmarks` and `post_reads`: deleting one user wiped the feeds they had added for everybody. **Never give `feeds.user_id` a cascading delete again, and never add one to `posts`.** The cascades on `feed_follows`, `bookmarks` and `post_reads` are correct and should stay — those rows belong to the user being deleted. `GetFeeds` therefore needs `LEFT JOIN users` with `COALESCE(users.name, '')`, which keeps `user_name` a plain `string` in sqlc; `gator feeds` omits the `Added by:` line when it is empty.

**Per-user post state.** `bookmarks` and `post_reads` both key on `(user_id, post_id)` with `ON CONFLICT DO NOTHING`, same as `feed_follows` — pressing a key twice must never surface a 23505. The TUI mirrors both into `map[uuid.UUID]bool` shared by reference with every `postItem`, so markers (`●` unread, `★` saved) update without rebuilding the list. Mutate those maps, never reassign them.

**TUI** (`internal/tui/`, in progress on branch `DEV-001_TUI`) uses Bubble Tea's Elm architecture — `Init`/`Update`/`View` on a `model`. `internal/cli/tui.go` stays a thin `tui.Run(ctx, s.Store, user)` wrapper behind `middlewareLoggedIn`; the model holds a `store.Store`, not `*database.Queries`, and no `userID`. `docs/tui-plan.md` is the phased plan being followed; it is the source of truth for this work. Two rules that matter: never do DB/HTTP/`exec` work directly inside `Update` (it blocks the event loop — wrap it in a `tea.Cmd`), and always forward `tea.WindowSizeMsg` dimensions to sub-components.

**Real accounts (`internal/auth`), still 100% local.** Migration 015 adds `users.email` (nullable, unique on `lower(email)`) and `users.password_hash` (`NOT NULL DEFAULT ''`); migration 016 adds `api_tokens` (`user_id` cascades — unlike `feeds.user_id`, a token *is* owned by the user). `password_hash = ''` is the local-only account shape and is what `gator init --user` and bare `register` (no flags, no terminal) still produce — `auth.VerifyPassword` never matches it, and nothing on the local path checks it anyway. `register [--email=] [--password=] <username>` prompts for both when it has a terminal and the flag was not given; flags must come before the username because the stdlib `flag` package stops parsing at the first positional argument. `auth.HashPassword` leans on `bcrypt.GenerateFromPassword` to reject passwords over 72 bytes itself (`bcrypt.ErrPasswordTooLong`) rather than duplicating that check — it does not silently truncate, which was the thing worth guarding against. `login` is unchanged: identity is still purely the username in `~/.gatorconfig.json`, and no command checks a password yet. `resolvePassword` treats a `term.ReadPassword` failure as "no password given" rather than aborting registration, because `isTerminal`'s `os.ModeCharDevice` check (see above) can claim a non-interactive fd is a terminal, and `term.ReadPassword`'s ioctl then fails. Tokens (`auth.GenerateToken`/`HashToken`, `gat_` prefix, 32 bytes, SHA-256 at rest) and the `CreateAPIToken`/`GetUserByTokenHash` queries exist for the server-auth phase (`docs/product-roadmap.md` Faza 3) — `internal/api` issues and checks them (see below).

**`gator serve` and the remote store (`internal/api`, `internal/store/remote`, `internal/wire`).** `serve` is an `allCommands()` entry, not a second binary. Every authed route resolves the bearer token with `GetUserByTokenHash` and then builds a `local.NewFor(q, user)` for that one request, so the server answers with the same `local.Store` the CLI uses and the "no `userID` argument" property carries over to HTTP unchanged. `remote.Store` is the client half of `store.Store`; `Refresh` returns `errors.ErrUnsupported` because the aggregator only ever runs next to Postgres. `internal/wire` holds the JSON shapes — `Post`, `Feed` and `User` have their own types because sqlc's `sql.Null*` would serialize as `{"String":..,"Valid":..}`, and `User` is what keeps `password_hash` off the wire. The rest (`Subscription`, `FeedStat`, `UnreadCount`, `Follow`) are plain sqlc rows sent as-is, so adding a column to those changes the API.

`internal/api/api_test.go` has the parity test: the same `PostQuery` against `local.Store` and `remote.Store` on one database, compared as JSON. It already caught one real bug — `since` crosses the wire as UTC but `timestamp` columns compare wall clocks, so the server must convert with `.In(time.Local)` before the query or a non-UTC server silently filters the wrong window.

Selecting the store: `open()` in `cli.go` builds `remote.New` when `config.ServerURL` is set (token from `~/.gatorcredentials.json`, `0600`, bound to that server URL) and leaves `state.Db`/`state.DB` nil. Entries marked `localOnly` (`feeds`, `agg`, `supervise`, `prune`, `users`, `reset`, `migrate`, `serve`) are refused in that mode by `guardLocal` and hidden from the menu. `login`, `register` and `logout` are `noDB`; their local path opens the database lazily through `state.withDB`. `login/register --server` refuses plain `http://` unless the host is loopback. `gator logout` revokes the token, deletes the credentials file and clears `server_url`.

Endpoints deviating from `docs/product-roadmap.md`: unfollow/categorize/follow take a feed **URL** (`DELETE /v1/subscriptions?url=`, `PATCH /v1/subscriptions`, `POST /v1/subscriptions/follow`) because `store.Store` is URL-keyed and a lookup-by-id round trip could not tell "unknown feed" from "not followed"; `DELETE /v1/subscriptions/{feed_id}` exists for `Unfollow`. Errors carry a `code` that `remote.Error.Is` maps back to `store.ErrFeedNotFound`/`ErrNotFollowed`/`ErrNoMoreText`. **`POST /v1/subscriptions` makes the server fetch an arbitrary URL and there is no SSRF guard or rate limit yet — that is Faza 4. Do not expose `serve` to strangers before it lands.**

**The feed catalog is verified against the live network, not just checked for shape.** `internal/catalog/catalog.json` is 54 categories and 424 feeds, embedded in the binary. Three tests guard it: `TestCatalogIsWellFormed` (kebab ids, absolute https, no duplicate URL), `TestEveryCategoryIsWorthBrowsing` (at least 4 feeds — a near-empty category looks broken in `gator discover`), and two network tests gated behind `GATOR_CATALOG_CHECK=1`, which fetch every feed through `rss.FetchFeed` and assert none is unreachable or empty, then compare per-category item links and fail when two feeds in one category overlap by more than 60%.

```bash
GATOR_CATALOG_CHECK=1 go test ./internal/catalog/ -timeout 10m
```

**Run that before adding catalog feeds, and after.** Of 301 candidate URLs collected by hand, 65 were dead on arrival and nine more passed a plain `curl` but failed gator's own parser — 8 MB-plus Blogger archives, feeds slower than the 10s `rss.FetchFeed` timeout, and `&nbsp;` in XML. The overlap test is the one that cannot be replaced by reading URLs: it caught `cyclingtips.com` and `velo.outsideonline.com` serving identical items after a rebrand, a blogspot mirror of a blog already listed under its own domain, and two NASA paths with the same content — while correctly allowing `motorsport.com`'s three separate series feeds, which a same-host rule would have rejected.

**`internal/rss` is stricter than other readers, and `encoding/xml` is why.** A bare `&nbsp;` makes `xml.Decoder` fail with `invalid character entity`, which is the single most common malformation in real feeds — four of the candidate URLs above died on it. Nothing substitutes HTML entities before decoding. That is a real gap for non-technical users, who see `XML syntax error on line 758` from `addfeed` and have no way to act on it; it is not the catalog's problem to work around.

**One `User-Agent`, in `internal/useragent`.** Both fetch paths (`rss.FetchFeed` and `article.Fetch`) send `useragent.String`. It must stay a conventional `name/version (+url)` token: the previous value was the bare word `gator`, and WAFs read a single-word agent as an unidentified bot — `locusmag.com` returned 403 to `gator` and 200 to anything with a version or URL in it. The string names the repository, so it lives in one place for the same reason the module path does.

## Code style

The maintainer is actively working toward **idiomatic Go** — prefer the idiomatic form even when a working alternative exists, and point out non-idiomatic patterns in code you touch.

**Do not write comments.** Code that is written by hand carries no comments — not in Go, not in SQL, not in YAML, and not doc comments on exported identifiers either. Explain the reasoning in the commit message or in `docs/`, where it can be read without cluttering the code. Two things are not covered by this rule: files sqlc generates (`internal/database/*.sql.go`), which are never hand-edited anyway, and the directives tools require to work — `-- name: ... :many` for sqlc and `-- +goose Up` / `-- +goose Down` in `sql/schema` — which are instructions to a program, not commentary. Comments already in the tree may stay; this governs what gets added.

Concretely, in this codebase:

- **Type switches over chained type assertions.** In Bubble Tea `Update`, use `switch msg := msg.(type)` with a `case` per message type, not nested `if v, ok := msg.(T); ok`.
- **`errors.Is` / `errors.As` over type assertions on errors** (see `feeds.isDuplicate`).
- **`%w` over `%v` when wrapping errors**, so callers can unwrap.
- **Thread `context.Context`** instead of calling `context.Background()` at every DB call site.
- Keep `gofmt` clean and errors on stderr, output on stdout.

Existing code does not fully follow these yet — improving it as you go is welcome, but keep refactors scoped to what the task touches.

## Notes

- `docs/` is gitignored (along with `*.log`) but present locally; `docs/refactor-plan.md` and `docs/roadmap.md` track known issues and planned features and are worth reading before larger changes.
- The maintainer writes in Serbian; all of `docs/` and the comments still left in the code are in Serbian. Match the language of surrounding text. User-facing CLI output and the README are in English.
- `browse` opens the TUI when stdout is a terminal; `--no-tui` (or a pipe) gives plain output. `--limit`/`--page`/`--feed`/`--sort` apply to plain output only.
- **Both fetch paths bound the response body at 8 MB, and neither truncates silently.** `rss.FetchFeed` reads through `readBody`, which takes `maxBody+1` bytes and returns `ErrBodyTooLarge` if it got more; a silently truncated feed is malformed XML, so a plain `io.LimitReader` would surface as a confusing parse error or, worse, parse with items quietly missing. `article.Fetch` wraps the body in a `boundedReader` that counts bytes and checks `exceeded()` **after** `Extract` returns — the post-check rather than the returned error, because go-readability is not guaranteed to propagate a reader error with `%w`. That one matters more than it looks: `fetchFullText` feeds the result to `article.Improves` and then `SetPostFullText`, so a truncated article would be accepted (it is longer than the feed's teaser) and cached in `posts.full_text` permanently, never refetched. Both limits are generous on purpose — the largest real feed is ~390 KB, the biggest HTML page discovery scans (theverge.com) ~906 KB, and the biggest real article page ~1.8 MB.
- `internal/rss` dispatches on the root element: `<rss>` (RSS 2.0), `<feed>` (Atom) and `<RDF>` (RSS 1.0) are all parsed and converted to the RSS 2.0 shape, so callers only ever see `Channel`/`Item`. Anything else fails with a `*rss.NotAFeedError` naming the root element. A `CharsetReader` backed by `golang.org/x/text` accepts feeds declaring ISO-8859-1 or windows-1252.
- Feed discovery runs on **any** body that is not a recognised feed, including one the XML tokenizer chokes on — YouTube's HTML has unquoted attributes, so `rootElement` fails before it can report `<html>`, and bailing there used to make channel pages unaddable. It also scans the **whole** document rather than stopping at `<body>`: YouTube puts its `<link rel="alternate">` about 750 KB in, below the body. Head links still win because document order is preserved.
- A YouTube channel URL therefore needs no special case: `addfeed` finds `feeds/videos.xml?channel_id=…` on the page. `atomEntry` reads `media:description` (`http://search.yahoo.com/mrss/`) because YouTube leaves `<summary>` and `<content>` empty, so without it every video is a bare title.
- When that root is `<html>`, the same error also carries the feeds the page advertises in `<link rel="alternate">`, read with `golang.org/x/net/html` out of the body already fetched — no second request. `feeds.resolve` takes the first (sites list the main feed before comments feeds) and stores **that** URL, so `addfeed` accepts a bare site address and `export` still writes the feed. Relative hrefs resolve against the URL the request finished on, after redirects.
- `rss.parseFeed` ends with `resolveBody`, which sets each item's `Description` to the longest text the feed offers — `<content:encoded>` (Atom: `<content>`) when present, `<description>` otherwise. Callers never choose. Posts already in the database keep their old short body, because `CreatePost` uses `ON CONFLICT DO NOTHING`.
- `gator stats` (`stats.go`) answers "which of these do I actually read". One query, `GetFeedStatsForUser`, returns volume, reads, bookmarks and the last post/read per followed feed. Two things there are deliberate: the 7-day window arrives as `@since::timestamp` from Go rather than `NOW()` in SQL, matching `GetPostsForUserFiltered`; and `MAX()` is wrapped in `COALESCE(..., '0001-01-01')` because sqlc types a cast aggregate as non-null `time.Time`, so a feed with no posts would panic on a NULL scan. Go reads that zero time as "never".
- `rss.Source` is what is remembered about a feed between fetches: its URL plus the conditional-GET validators. `FetchFeed` takes one and returns the next, and `Source.URL` changes **only** when every hop in the redirect chain was `301`/`308` — a `CheckRedirect` hook watches `req.Response.StatusCode` for that, since `res.Request.URL` alone cannot tell a permanent move from a temporary one. `feeds.Scrape` then writes it back with `SetFeedUrl`, tolerating `23505` because two feeds can redirect onto the same address. Of the maintainer's 49 feeds, 10 redirect permanently.
- Feed health lives on `feeds`: `etag`/`last_modified` (conditional GET) and `last_error`/`failure_count`. `feeds.Scrape` records health **only around `rss.FetchFeed`** — a database write failing is not the feed's fault — and a `304` counts as success. `gator feeds` prints `⚠ failing since N attempt(s)`, the TUI feed pane prefixes the name with `⚠`.
- `internal/opml` reads and writes subscription lists. `Parse` walks arbitrarily nested outlines, treats any outline without an `xmlUrl` as a folder, and keeps the first occurrence of a duplicate URL. `import`/`export` accept `-` for stdin/stdout, and export's summary goes to stderr so the OPML can be piped.
- Folders survive the OPML round trip. They live on `feed_follows.category` (per user — the same feed can sit in different folders for different people): `import` keeps them, `export` groups by them (folders alphabetical, uncategorized last), `discover --add` writes the catalog label, and `gator categorize <url> <folder>` moves one by hand. The TUI feed pane groups by them too, collapsed by default, with which folders are open persisted in `~/.gator-state.json`.
- **The feed pane numbers only its first nine folders, and deliberately does not pad the rest.** `1`-`9` jump to a folder (select, expand, focus the pane), `[`/`]` step between folder headers without expanding, `0`/`-` collapse/expand all. The number is printed in the label (`1 ▸ Basketball (211)`) because a shortcut nobody can see is a shortcut nobody uses — at 22 folders the pane does not fit on one screen, so counting is not an option. The label budget is **23 columns** (`feedPanelWidth` 26 minus the gutter minus the delegate's 2), and the first attempt padded folders 10+ by two spaces to keep the arrows in one column. Measured against the real database, that turned `Web development (119)` into `Web development (1…` — and **a truncated count reads as a smaller number, not as a truncated one**. The padding is gone: folders past nine are byte-identical to how they rendered before, feeds stay visibly nested under them, and only the numbered nine pay the two columns. Any change that lengthens a folder label hits the same wall, so measure the rendered pane rather than counting characters.
- **`keyMap.fullHelp()` must stay at five columns, and a short help line's budget is 73, not 80.** `help.Model` silently truncates to its `Width`, so at 80 columns a sixth column is simply not drawn — `n next`, `p prev`, `? help` and `q quit` were invisible in `?` for as long as there were six. Five columns of seven bindings render at width 71. The short lines are tighter than they look: `userTagged` appends `@marko` only while `width - line - tag >= 1`, so a short help over **73** columns makes the user tag vanish with no other symptom. That is what adding `: commands` did to the post list before it was caught. The palette changes what the short help is for — it is four frequent keys plus the two doors (`:` and `?`), not a catalogue — so `s search` and `d unfollow` live in the palette and in `?` instead. `TestEveryFooterFitsEightyColumnsWithRoomForTheUserTag` and `TestEveryBoundKeyAppearsInTheFullHelp` are the guards; a new binding means re-measuring, not assuming.
- **The command palette is a fourth `list.Model`, not a new fuzzy layer.** `list.DefaultFilter` is already `fuzzy.Find` + `sort.Stable` with `MatchedIndexes` for highlighting, so `openPalette` just starts a list in `list.Filtering` state and inherits ranking, match highlighting and pagination. Three things about that state are counter-intuitive. `list` **disables `CursorUp`/`CursorDown` while filtering**, so `updatePalette` calls them itself before delegating — otherwise typing works and the arrows do nothing. `enter` and `esc` belong to the list while filtering (`AcceptWhileFiltering`, `CancelWhileFiltering`), so they are intercepted first. And filtering is **asynchronous**: `Update` returns a `tea.Cmd` that yields a `FilterMatchesMsg`, which `model.Update` must route to the palette — it used to fall through to `m.list`, the posts list, so the palette would never have filtered in production. A test caught that, not reading.
- **A list item's `FilterValue()` must be a prefix of its `Title()`.** `list` computes `MatchedIndexes` over `FilterValue()` and applies the highlight to `Title()`, so when they differ the wrong characters are underlined. `paletteItem` therefore returns the bare label from `FilterValue()` and label-plus-padding-plus-key-hint from `Title()`. `postItem` does *not* satisfy this (its `Title()` is prefixed with `●`/`★`), so `/` filtering in the post list already highlights shifted characters; the feed pane is unaffected only because filtering is disabled there.
- **Remote failures reach the UI as `store` sentinels, never as HTTP status codes.** `store.ErrUnauthorized` (401 or 403), `store.ErrPlanLimit` (402) and `store.ErrUnreachable` (a failed `client.Do`, wrapped with two `%w` so the dial error survives) are mapped in `remote.Error.Is` and in `remote.do`, so `internal/tui` and `internal/cli` match with `errors.Is` and never import the transport. `tui.explain` turns each into a sentence and `tui.fatalView` picks the matching instruction — `q` to quit, but `r` to retry when the server is merely unreachable. Do not add a `wire.Code…` case for something the status already covers: `CodeUnauthorized` was one, and deleting it broke no test because every route that sends it uses 401. **402 cannot occur yet** — billing is Faza 5 and `StatusPaymentRequired` appears nowhere in `internal/api` — so its test exercises the mapping, not a real server path.
- **The TUI learns it is remote from `cli.open()`, not from the store.** `tui.Run` takes a `server string` (`s.Cfg.ServerURL`; empty means local) because that is where the local-or-remote decision is made, and passing the URL rather than a bool is what lets the messages name the server. In remote mode `fetchAll` refuses `R` without calling the store at all, `keyMap.fullHelp(remote)` drops `R fetch`, and `paletteItem.localOnly` hides "Fetch feeds now" — the same `localOnly` idea `allCommands()` uses. Everything else stays, because the server does support `AddFeed`, the catalog, `categorize` and `unfollow`.
- **Folders are palette entries, which is what finishes the numeric shortcuts.** The palette lists its actions plus one `Folder: <name>` entry per folder, so the thirteen folders the digits cannot reach are still findable by name (`:` then `web`). The palette is also the only way to reach `store.Categorize` from the TUI — `gator categorize` was the sole route before — and a successful move expands the destination folder, or the feed looks like it vanished.
- `printPost` prints a bounded preview: `internal/text` strips the HTML and `Truncate` cuts on a word boundary at 400 runes. The full body is only shown in the TUI. `internal/text` is the shared home for both — the TUI detail pane uses `StripHTML` too.
- **`PrunePosts` keeps a post if any of three things is true**: it is bookmarked, it is newer than the retention window, **or it is among the newest `keep_per_feed` of its feed** (`feeds.DefaultKeepPerFeed` = 10, `prune --keep-per-feed N`). `--keep-per-feed 0` gives the old age-only semantics. The `row_number()` window ranks **all** of a feed's posts, not just the old ones — ranking only the old ones would make a feed with 50 fresh posts needlessly retain 10 stale ones. Why the third clause exists, measured: under age-only pruning, 54 of the maintainer's 59 empty feeds had been fetched successfully *in the same tick* and then pruned away — The Go Blog, Dave Cheney, Scott Hanselman, web.dev. They were not broken, just slower than 72 hours. Median posts per followed feed went 2 → 10 and empty feeds 59 → 0. Changing this query's semantics is its own commit.
- **Conditional GET and pruning fight each other, and pruning wins permanently.** If `PrunePosts` empties a feed, the stored `etag`/`last_modified` make the next fetch a `304`, so gator never re-reads the items it deleted — the feed stays empty until the publisher posts something new. That is not hypothetical: after the `keep_per_feed` change, 34 feeds were still empty and **all 34 had returned `304`**; they only recovered after a one-off `UPDATE feeds SET etag='', last_modified=''` for feeds holding fewer than 10 posts. **Any change that lowers retention leaves the same scar.** The self-healing fix — have `Scrape` ignore the stored `rss.Source` when a feed holds fewer than `keep_per_feed` posts — needs a post count in `GetFeedsToFetch` and is not implemented.
- **State keyed on `post_id` evaporates unless `PrunePosts` protects it**, and nothing fails when it does. `PrunePosts` deletes any post past the 72h retention that is not bookmarked, `prune` runs on every `agg` tick, and `posts.url` is UNIQUE — so the post comes back from the feed with a fresh UUID and the state is simply gone. Measured on real feeds, 29% of what the busiest feed serves is already past retention, so this bites hardest on exactly the feeds such a feature would be for. Any new table keyed on `post_id` needs a matching `NOT EXISTS` clause in `PrunePosts`, which changes retention semantics and belongs in its own commit.
- **Everything that orders posts uses `COALESCE(posts.published_at, posts.created_at)`** — `GetPostsForUserFiltered` (both the `ORDER BY` and the `@since` comparison), `SearchPostsForUser`, `PrunePosts`, and `stats`' `recent_count`/`last_published`. Without it, a post with no publish date sinks below every dated one forever: measured on the real database, a dateless post sat at position **2124 of 2231**. `NULLS LAST` is gone from those clauses because the expression can no longer be null. `GetPostsForUser` was deleted in the same change — nothing used it, and it was the only query with a bare `DESC`, which in Postgres puts NULLs *first*.
- **Before reaching for that fallback, check whether the date is really absent or just unparsed.** It was mostly unparsed. Three gaps cost 53 posts their real publication date: `RSSItem` read only `pubDate` and ignored `dc:date` (A List Apart ships RSS 2.0 with Dublin Core dates — `rdfFeed` already read `date` unqualified, so RSS 1.0 was never affected); `ParsePubDate` did not trim, so a pretty-printed `<dc:date>\n\t\t\t2026-…\t\t</dc:date>` failed every layout; and `pubDateFormats` had no unpadded-day layout, so `Wed, 8 Apr 2026 00:00:00 +0000` from MDN Blog and Golang Weekly parsed as nothing. The `dc:date` fallback lives in `resolveBody` (`firstNonEmpty(it.PubDate, it.Date)`) so callers still only ever read `PubDate`, the same way `Description` is resolved. New posts now arrive dateless at 1.3% instead of 5.7%, and the remaining ones are genuinely undated at source — CBS Sports sends 0 dates for 36 items, Formula 1 0 for 10, BBC Good Food 2 for 10.
- **A date-parsing fix does not repair posts already stored.** `CreatePost` is `ON CONFLICT DO NOTHING`, so a re-fetched post keeps its old NULL `published_at`. The 53 above only recovered because their rows were deleted and refetched. Any future parsing fix needs the same step, or it only applies to what arrives next.
- `MarkFeedHealthy` ends with `AND (last_error <> '' OR failure_count <> 0)` so it skips the write for feeds that were already healthy — the majority every round. Adding a column to that query inherits the narrowing silently. If a `last_synced_at` is ever wanted, write it **on the failing → healthy transition** and keep the guard: that gives "last worked" for the feeds that need it without a write per feed per round, which is what the guard exists to avoid.
